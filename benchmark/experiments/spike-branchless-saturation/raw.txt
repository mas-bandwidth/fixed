## disassembly (objdump -d, -O3 -DNDEBUG -ffp-contract=off, Apple clang 17, x86-64)

Compiled a function wrapper per arm (with -DFIX_SATURATE) and disassembled. Branch (jcc)
vs conditional-move (cmov/setcc) verdict per arm:

  fixMul (FIX_SATURATE)      : 0 jcc ; two cmovgeq saturation selects. ALREADY BRANCHLESS.
  fixDiv (FIX_SATURATE)      : the +-FIX_MAX tail is 2x cmovnsq (branchless). The jcc in the
                               body (je at b==0, ja/je at the |a|<2^47 fast path, jl in the
                               128-bit dispatch) are the divide dispatch and the div-by-zero
                               guard, NOT the saturation select.
  fixClamp / fixMin / fixMax : 0 jcc ; cmovlq/cmovgeq/cmovgq. ALREADY BRANCHLESS.
  fixFloor / fixCeil         : pure and/mask, 0 jcc, 0 cmov.
  fixQuantizeClamped         : 3 jcc (jae <-2^63, jae >=2^63, jl raw<minRaw). THE ONLY
                               conditional branch in the named set.
  fix30FromFix / fix30FromDouble : 2 jcc each (jg/jl domain saturation) -- NOT in the
                               card's named set.

So the hypothesis -- "the saturating arms ... use branches that mispredict" -- is falsified
on this compiler/ISA for every named arithmetic arm EXCEPT fixQuantizeClamped: clang already
lowers all the scalar ternaries to cmov/csel.

## before/after: fixQuantizeClamped inline branchy vs inline branchless

Fair microbenchmark: both bodies always_inline, same compiler/flags, xoshiro seed,
4096-input batch, 20,000,000 iterations, scalar (dependent-chain latency) and batch
(throughput). mode 0 = all in range; 1 = 1% saturate; 2 = 50% saturate.

                branchy_lat  branchless_lat  speedup   branchy_thr  branchless_thr  speedup
  mode 0       7.7993       4.8631          1.604     2.2764       2.8103          0.810
  mode 1       8.0023       4.8871          1.637     2.3471       3.0121          0.779
  mode 2       7.6749       4.8569          1.580     3.0424       6.2209          0.489

Latency improves ~1.6x (the dependent chain benefits from no branch); throughput REGRESSES
a large amount because the branchless form executes the double->int64 conversion (cvttsd2si)
unconditionally every call, and the branchy form early-exits on a perfectly-predicted
in-range branch. This is exactly the trap fixed3d's CLAUDE.md warned about: the OOO core
hides the branch-fetch latency in the throughput loop, and removing the branch forces the
conversion + clamp chain every time. For a mix where most lanes are in range, branchy wins.
